# 体育场馆预约系统任务拆分

本文档按 `to-issues` 的垂直切片思路拆分任务。每个任务尽量覆盖数据库模型、业务逻辑、页面/API、权限和测试，完成后应能独立演示或验证。

## 任务 1：确认首期技术栈与项目骨架

**Type**: HITL

**Blocked by**: None - can start immediately

**User stories covered**: 48, 49, 50

### What to build

确认首期采用 Django + MySQL + Django Templates 的 Web 实现路线，创建项目骨架、应用模块、基础配置、环境变量配置方式和本地运行说明。

### Acceptance criteria

- [ ] 项目可以在 `sports_stadium` 环境中启动开发服务器。
- [ ] 项目包含账户、场馆、预约、评论等清晰应用模块。
- [ ] 配置文件支持本地开发数据库配置，不把敏感信息写死在代码里。
- [ ] README 或开发文档说明如何安装依赖、迁移数据库、启动项目。
- [ ] 基础健康页面或首页可访问。

## 任务 2：实现用户模型、角色与基础权限

**Type**: AFK

**Blocked by**: 任务 1

**User stories covered**: 8, 12, 13, 48

### What to build

建立系统的用户与角色基础。系统应明确支持普通用户、场馆管理员、系统管理员三类角色，并提供统一的权限判断能力，让后续场馆、预约、评论功能可以复用。

### Acceptance criteria

- [ ] 用户具有手机号、昵称、角色、账户状态等必要字段。
- [ ] 系统能区分普通用户、场馆管理员、系统管理员。
- [ ] 已禁用或注销用户不能继续登录或执行受保护操作。
- [ ] 权限判断覆盖普通用户不能执行后台审核、场馆管理员只能管理自己资源等基础边界。
- [ ] 角色和权限逻辑有自动化测试。

## 任务 3：实现注册、登录与退出闭环

**Type**: AFK

**Blocked by**: 任务 2

**User stories covered**: 1, 2, 3, 4, 5, 6, 46, 47

### What to build

实现普通用户注册、登录、验证码登录占位能力和退出功能。验证码可先使用开发 stub，保留后续替换真实短信服务的接口。

### Acceptance criteria

- [ ] 用户可以使用手机号和密码注册。
- [ ] 重复手机号注册会失败并展示清晰错误。
- [ ] 两次密码不一致会失败并展示清晰错误。
- [ ] 注册流程包含验证码校验，首期可使用开发环境固定验证码或 stub。
- [ ] 用户可以使用手机号和密码登录。
- [ ] 用户可以退出登录。
- [ ] 登录、注册失败不会泄露敏感信息。
- [ ] 注册和登录流程有页面级或集成测试。

## 任务 4：实现个人资料、密码找回与账号注销

**Type**: AFK

**Blocked by**: 任务 3

**User stories covered**: 7, 8, 9, 10, 11, 46

### What to build

实现用户查看个人资料、修改昵称/联系方式、修改密码、找回密码和注销账号。敏感操作需要密码或验证码验证。

### Acceptance criteria

- [ ] 登录用户可以查看个人资料。
- [ ] 登录用户可以修改允许修改的个人资料。
- [ ] 用户可以通过原密码或验证码修改密码。
- [ ] 用户可以通过手机号和验证码重置忘记的密码。
- [ ] 用户可以注销自己的账号，注销后不能再登录。
- [ ] 修改密码、找回密码、注销账号有自动化测试。

## 任务 5：实现场馆提交与系统管理员审核

**Type**: AFK

**Blocked by**: 任务 3

**User stories covered**: 17, 18, 19, 20, 21, 48, 50

### What to build

实现场馆管理员提交场馆、编辑场馆、申请删除场馆，系统管理员审核通过或退回。只有审核通过的场馆对普通用户可见。

### Acceptance criteria

- [ ] 场馆管理员可以提交场馆名称、地址、联系电话、简介等信息。
- [ ] 新场馆默认进入待审核状态。
- [ ] 系统管理员可以查看待审核场馆并批准或拒绝。
- [ ] 审核通过后场馆对用户可见。
- [ ] 审核拒绝后场馆不对用户可见，并保留拒绝状态。
- [ ] 场馆管理员只能编辑或删除申请自己负责的场馆。
- [ ] 场馆审核流程有自动化测试。

## 任务 6：实现公开场馆列表、详情与搜索

**Type**: AFK

**Blocked by**: 任务 5

**User stories covered**: 14, 15, 16, 43, 47

### What to build

实现用户侧可访问的场馆列表、场馆详情和按名称搜索。列表和详情只展示已审核通过、处于开放状态的场馆。

### Acceptance criteria

- [ ] 用户可以查看已通过审核的场馆列表。
- [ ] 未审核或审核拒绝的场馆不会出现在公开列表。
- [ ] 用户可以按场馆名称搜索。
- [ ] 用户可以进入场馆详情页查看地址、联系方式、简介等信息。
- [ ] 公开场馆查询有自动化测试。

## 任务 7：实现场地管理

**Type**: AFK

**Blocked by**: 任务 5

**User stories covered**: 22, 23, 24, 25, 26, 48

### What to build

实现场馆管理员在已审核通过的场馆下创建、编辑、停用或删除场地。场地应包含类型、编号、状态和预约单价等信息。

### Acceptance criteria

- [ ] 场馆管理员只能在自己负责且已审核通过的场馆下创建场地。
- [ ] 场地包含类型、编号、状态、单价等必要信息。
- [ ] 场馆管理员可以编辑自己场地的信息。
- [ ] 停用场地后用户不能继续预约该场地。
- [ ] 普通用户可以在场馆详情中看到可用场地和价格。
- [ ] 场地权限和可见性有自动化测试。

## 任务 8：实现时段管理与冲突校验

**Type**: AFK

**Blocked by**: 任务 7

**User stories covered**: 27, 28, 29, 30, 31, 32, 49

### What to build

实现场馆管理员为场地创建、修改和删除开放时段。系统必须阻止同一场地出现重叠时段。

### Acceptance criteria

- [ ] 场馆管理员可以给自己管理的场地新增开放时段。
- [ ] 时段包含日期或适用日期、开始时间、结束时间、可约状态。
- [ ] 同一场地的重叠时段会被拒绝。
- [ ] 场馆管理员可以修改或删除自己场地的时段。
- [ ] 用户可以在场馆/场地详情中看到时段可约状态。
- [ ] 时段冲突校验有自动化测试。

## 任务 9：实现用户提交预约与查看我的预约

**Type**: AFK

**Blocked by**: 任务 8

**User stories covered**: 31, 32, 33, 34, 46, 47, 49

### What to build

实现普通用户选择场馆、场地和时段提交预约申请，并查看自己的预约列表。预约提交后进入待审核状态。

### Acceptance criteria

- [ ] 普通用户可以对开放场地的可约时段提交预约申请。
- [ ] 未登录用户不能提交预约。
- [ ] 不可约、已占用或已停用场地/时段不能提交预约。
- [ ] 提交成功后预约状态为待审核。
- [ ] 用户可以查看自己的预约列表和预约状态。
- [ ] 预约提交和“我的预约”有自动化测试。

## 任务 10：实现预约审核、冲突防护与取消

**Type**: AFK

**Blocked by**: 任务 9

**User stories covered**: 35, 36, 37, 38, 39, 49, 50

### What to build

实现场馆管理员审核自己场地的预约申请，普通用户取消自己的预约。系统必须防止同一场地同一时段被重复批准。

### Acceptance criteria

- [ ] 场馆管理员可以查看自己场地的待审核预约。
- [ ] 场馆管理员可以批准或拒绝预约。
- [ ] 非场馆负责人不能审核该场地预约。
- [ ] 批准预约时，如果同一场地同一时段已有批准预约，则操作失败。
- [ ] 用户可以取消自己的待审核或已批准预约。
- [ ] 被取消的预约不再占用时段。
- [ ] 预约审核、冲突防护、取消流程有自动化测试。

## 任务 11：实现评论提交、审核与展示

**Type**: AFK

**Blocked by**: 任务 6

**User stories covered**: 40, 41, 42, 43, 44, 45, 50

### What to build

实现用户在场馆详情页提交评论，系统管理员审核评论，公开页面只展示审核通过的评论。用户可以删除自己的评论，管理员可以删除任意评论。

### Acceptance criteria

- [ ] 登录用户可以在场馆详情页提交评论。
- [ ] 新评论默认进入待审核状态。
- [ ] 待审核和审核拒绝评论不对普通用户公开展示。
- [ ] 系统管理员可以批准或拒绝评论。
- [ ] 用户可以删除自己的评论。
- [ ] 系统管理员可以删除任意评论。
- [ ] 评论审核和展示有自动化测试。

## 任务 12：实现系统管理员用户管理

**Type**: AFK

**Blocked by**: 任务 2

**User stories covered**: 12, 13, 48

### What to build

实现系统管理员查询用户、查看用户基本信息、禁用或注销非管理员用户账号。

### Acceptance criteria

- [ ] 系统管理员可以按手机号或昵称查询用户。
- [ ] 系统管理员可以查看用户角色和账户状态。
- [ ] 系统管理员可以禁用或注销普通用户和场馆管理员。
- [ ] 系统管理员不能误禁用最后一个系统管理员账号。
- [ ] 非系统管理员不能访问用户管理功能。
- [ ] 用户管理权限有自动化测试。

## 任务 13：整理首个可演示主流程

**Type**: AFK

**Blocked by**: 任务 3, 任务 5, 任务 7, 任务 8, 任务 9, 任务 10

**User stories covered**: 14, 16, 31, 33, 34, 36, 37, 47

### What to build

打通首个端到端演示流程：普通用户登录后浏览已发布场馆，选择场地和时段提交预约，场馆管理员审核通过，用户看到预约状态更新。

### Acceptance criteria

- [ ] 项目包含可复现的演示数据或数据创建说明。
- [ ] 演示流程从用户登录到预约审核完整可跑通。
- [ ] 页面之间导航清晰，用户能自然完成主流程。
- [ ] 主流程有至少一个端到端集成测试。
- [ ] README 记录演示账号和演示步骤。

## 任务 14：补齐基础 UI 与错误反馈

**Type**: AFK

**Blocked by**: 任务 13

**User stories covered**: 46, 47

### What to build

统一 Web 页面布局、导航、表单错误提示、成功提示和空状态，让系统达到课程项目演示可用的体验。

### Acceptance criteria

- [ ] 普通用户、场馆管理员、系统管理员登录后看到符合角色的入口。
- [ ] 表单错误信息清晰可见。
- [ ] 成功操作有明确反馈。
- [ ] 空列表页面有合理提示。
- [ ] 常用页面在桌面浏览器和手机宽度下不出现明显布局错乱。
